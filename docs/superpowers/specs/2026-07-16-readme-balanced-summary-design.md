# README バランス要約設計

## 目的

README を、利用者と導入者が必要な情報を一つの文書で把握できる長さへ整理する。詳細な内部実装や個別テストケースの列挙は避ける一方、フェーズ別の経緯、主要仕様、手動確認、変更履歴は要約して残す。

## 方針

- 厳密な行数上限は設けず、重複と内部実装の説明を優先して削る。
- 現在利用できる機能と運用上必要な情報を中心に書く。
- v2.0.0 の個別変更点は GitHub Release を正本とし、README では機能の全体像だけを示す。
- 既存データとの互換性、初期設定の再実行、対応形式、主要な件数・容量上限は残す。
- API名、状態遷移、内部クラス、詳細な失敗コード、フェーズ内の実装手順は削る。

## README 構成

1. 製品概要
2. 主な機能
3. 対応環境・技術構成
4. 安全設計と外部サービス上の注意
5. セットアップとデプロイ
6. データ構造と主要上限
7. フェーズ別概要
8. テストと手動確認
9. バージョン履歴とリリースノート
10. ライセンス

## 要約基準

### フェーズ別説明

複数写真、CSV／GeoJSONポイント、GPX／GeoJSONトラック、写真とトラック時刻の照合、Drive写真、UI統合を機能単位にまとめ、各項目を1〜3文で説明する。実装クラス名や処理経路は記載しない。

### 仕様

保存先シートの用途、対応ファイル形式、編集・共有の権限モデル、インポート件数、ファイル容量、トラック点数など、利用・導入判断に必要な値だけを残す。列単位の詳細や内部データ表現は省略する。

### 手動確認

個別ケースのチェックリストを、初期設定、写真取込、データ交換、トラック取込、共有表示、端末・ブラウザ互換の6カテゴリへ集約する。Apps Script・実ブラウザ確認が未実施である事実は明記する。

### 変更履歴

各バージョンを1行程度で要約し、v2.0.0以降はGitHub Releaseを詳細の参照先にする。コミットの列挙は行わない。

## 検証

- Markdownの見出し構造、リンク、コードブロックを目視確認する。
- READMEに依存する既存テストを含め、`node --test tests/*.test.js`を実行する。
- `git diff --check`で空白エラーを確認する。
- リリースノートとの矛盾、未実施の実機確認を確認済みと誤記していないこと、破壊的変更の有無を再確認する。

## リリースへの反映

README要約を通常のドキュメントコミットとして`master`へ追加する。公開前の`v2.0.0`タグをその最終コミットへ更新し、承認済みの日本語リリースノートでGitHub Releaseを公開する。公開確認後に`v1.4.0`ブランチをローカル・リモートから削除する。
