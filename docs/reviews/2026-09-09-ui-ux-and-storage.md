## 指摘事項

### F01 / P1 / 撮影日時が再読み込みで空になり、編集保存で元の日時も消せてしまう

**実画面・実シート・ローカル再現。**

登録直後の既存タブでは撮影日時が表示されていたが、同じ `/dev` を新しいタブで開くと、9件とも登録日時の表示になった。写真詳細は「イベント時刻: 未設定」、編集フォームの日時欄も空。実シート `map_info!M2` には撮影日時が残っている。エクスポートでも M2:M10 は日付書式の数値セルだった。

`PinData.normalizeEventAt` は `YYYY-MM-DDTHH:mm` 形式の文字列だけを受け付ける。`rowToPin` はシートからの `Date` 値もそのまま渡すため、空文字になる。登録時の応答では書き込み前の配列を使うので、一時的に正常に見える。

さらに編集フォームは空の `eventAt` を常に送信し、バックエンドは M 列を空に上書きする。ローカルでこの書き込みまで再現済み。**実シートでの保存は行っていない。** タイトルだけ直すつもりでも日時を消す可能性があり、日時順・ルートの時系列順・共有表示にも影響する。

- 箇所: `Code.js:64`、`:189`、`:5584`、`:7048`、`:8689`、`index.html:17744`、`:23750`。
- 修正案: シートのタイムゾーンを考慮した `Date` 読み取りと、日時を文字列で保存する規約を揃える。既存の日付セルも読める互換性を維持する。文字列だけのテストに加えて、実際の `Date` 値を返す読み取り・保存・再読込の往復を検証する。

### F02 / P1 / ピン編集の文字列がスプレッドシートの数式として保存される

**ローカル再現・Google仕様確認。**

新規登録には `encodeSpreadsheetLiteral_` があるが、`updatePinDetails` はタイトル・説明・タグを直接 `setValues` に渡す。`=1+1`、`=2+2`、`=3+3` が未エスケープでそれぞれの列へ渡ることを再現した。

Googleの `Range.setValues` は `=` から始まる値を数式として解釈するため、例えば文字として保存した `=1+1` が、再読込では計算結果として扱われる。編集時だけ文字列保存の保護が外れている。実データへ数式は送信していない。[Google Range仕様](https://developers.google.com/apps-script/reference/spreadsheet/range#setValues(Object))

- 箇所: `Code.js:9`、`:5595`、`:8674`、`:8696`、`:8700`。
- 修正案: ユーザーが入力した文字列の書き込みを共通の可逆エンコードに統一する。既存の意図的な数式を保持する処理とは区別する。複製・一括編集も同じ規約で確認する。

### F03 / P2 / ピン編集の保存中に再保存・キャンセルができ、古い応答が次の編集画面を閉じる

**実イベントハンドラのローカル再現。**

通常のピン編集には保存中フラグ、保存ボタンの無効化、応答の世代確認がない。遅延させた保存応答で次を再現した。

1. 保存を2回押すと、応答待ちでも更新要求が2件発行される。
2. 保存待ちでキャンセルし、別のピンを編集状態にする。
3. 前の応答が返ると `editingPinId` が `null` になり、新しい編集画面も閉じられる。

スプレッドシートのロックは同時書き込みを直列にするが、古い画面の応答処理までは防がない。`beforeunload` 用の未完了処理判定にも通常のピン編集保存が含まれていない。

- 箇所: `index.html:23731`、`:23738`、`:23770`、`:25283`。
- 修正案: 保存中の二重送信防止、キャンセル方針の明示、編集セッションとピンIDを照合した応答処理、離脱警告への組み込み。通信遅延・エラー・キャンセル後の別ピン編集を検証する。

### F04 / P2 / 起動待ちが長く、独立した読み込みまで直列になっている

**実画面で2回計測・コード確認。**

このPC・Chrome・既存ログイン・写真ピン9件・GPX1件498点で、再読込の開始から「ピンを追加」が有効になるまで **12,810 ms / 17,663 ms** を観測した。ブラウザ操作と状態検出の時間も含む端末側の観測値であり、GASだけの処理時間や一般利用者の平均値ではない。

起動順は `getAppSettings` → `getMapData` と `getRouteGroups` の完了待ち → `getTracks`。ピンはルート取得も終わるまで描画されない。編集操作はトラック読み込みを含む初期化完了を待つ。ピン描画と一覧描画も、初回読込時と初期化末尾で繰り返される。

- 箇所: `index.html:29054`、`:30188`、`:30205`、`:30217`、`:30234`。
- 修正案: 依存しない読込を並行化し、ピン・ルート・設定の準備状態を分ける。安全に操作できる機能から開放し、未完了の領域だけ読込表示を残す。描画の重複を減らす。改善量はGAS各段階の計測で検証する。
- 拡大時の懸念: `getTracks` は非表示を含む全トラックと全座標を読み、復元・集計して返す（`Code.js:4144`）。少数件ではDB移行よりこの読込設計の改善を優先する。

### F05 / P2 / ルートの読み込み失敗・一部破損を画面上で区別できない

**コード確認。故障の実注入はしていない。**

`getRouteGroups` の失敗では `console.error` の後に空配列を設定する。`getTracks` の失敗でも空配列で再描画する。バックエンドが個別の破損を `warnings` で返した場合も `console.warn` のみ。利用者には「保存済みルートがない」のか「読めなかった」のかが分からない。

- 箇所: `index.html:29064`、`:29129`、`:29143`、`:30218`。
- 修正案: 正常な0件と読込失敗・一部失敗を別状態にする。対象領域に件数付きの警告と再試行を置く。成功済みの既存表示は維持する。

### F06 / P2 / 道路ルートのキャッシュは1セルへ無制限にJSONを書き込む

**ローカル再現。実シートには大きな値を書いていない。**

`putRouteCache` は座標数・JSON長を制限せず、C列へ全座標を格納する。4,000点の合成座標で **91,105文字** が1セルの書き込みに渡った。対照的にGPXの `track_segments` は500点・40,000文字以下へ分割される。

長い道路ルートではセル容量でキャッシュ保存が失敗するリスクがある。クライアントは失敗をコンソールに出すだけでメモリキャッシュを保持するため、そのセッションでは気づきにくく、再読込後に再計算が必要になる。Googleのファイル制限資料でも50,000文字を超えるセルがSheets変換時に保持されないことが明記されている。実GASでの上限境界は追加検証が必要。[Googleのファイル制限](https://support.google.com/drive/answer/37603?hl=ja)

- 箇所: `Code.js:2827`、`:2880`、`:2892`、`index.html:21167`。
- 修正案: キャッシュJSONにも上限・簡略化・分割保存を設ける。期限切れを表す `expiresAt` は現在空で、読み取り側も期限判定していないため、保持期間を実装するか予約列だと明示する。

### F07 / P2 / 起動診断パネルのURL指定が実GASでは効かない

**実画面・コード確認。**

編集用 `/dev` に `debugStartup=1` を付けても診断パネルは表示されなかった。判定は `window.location.search` を読んでいるが、GAS内側のフレームURLは `userCodeAppPanel?createOAuthDialog=true` で、外側のパラメータが入らない。`doGet` からこのフラグをテンプレートへ渡す処理もない。

- 箇所: `index.html:4809`、`:5019`、`Code.js:471`。
- 修正案: 編集権限の条件を維持し、`doGet` で明示的に渡すか、GAS用のURL取得APIを使う。既存テストは文字列引数での判定のみで、フレーム境界を検証していない。[GoogleのURL取得API](https://developers.google.com/apps-script/guides/html/reference/url)

### F08 / P3 / テンプレートの条件タグが画面に文字として出る

**実画面確認。**

ページ末尾に `<? if (editToken) { ?> <? } ?>` がテキストとして出て、アクセシビリティツリーにも含まれる。実GASへのHTML配信・評価の経路を通した問題で、ローカルのテンプレート置換テストでは検知できていない。

### F09 / P2 / 地図上のピンにアクセシブルな名前がない

**実画面・コード確認。**

9個の地図マーカーが、アクセシビリティツリーでは名前のないボタンとして現れた。キーボードや読み上げで地図を操作すると、どの写真・地点なのか区別しづらい。一覧の行には名前があるが、地図の操作対象には伝わっていない。

- 修正案: マーカーの名前へピンのタイトルを付ける。重なる地点、番号表示、フィルタ後の再生成でも名前とキーボード操作を検証する。

### F10 / P2 / Drive共有エラーを「組織ポリシー」と断定する

**今回の実履歴・コード・直前の登録障害で確認。**

`DRIVE_LINK_SHARING_DENIED` の表示文が、原因を組織の共有ポリシーに限定している。一方、実装は設定後の権限が完全に `VIEW` と一致しない場合にも同じコードを返す。親フォルダから継承した編集権限でも該当し、個人アカウント利用者をWorkspace管理者への問い合わせへ誘導してしまう。

現行データにはこのコードの過去の失敗履歴が25件、成功した取込が9件ある。現在の登録は成功しており、障害が続いているという意味ではない。

- 箇所: `Code.js:5237`、`:6891`、`:6909`、`index.html:11931`。
- 修正案: 保存先の権限、親からの継承、組織側制限を区別できる診断にする。判別できない場合は共有設定を確認する案内にし、管理者が原因だと断定しない。

## スプレッドシートは必要十分か

**現機能では10シートとも役割がある。空シートを減らすための統合・削除は不要。** 実エクスポートの各ヘッダーをコード定義と照合し、config以外の9シートすべて一致した。configは5設定行を確認し、秘密値はレポートに含めていない。

| シート | 列数 | 現在のデータ行 | 役割・判断 |
| --- | ---: | ---: | --- |
| config | 設定キー・値 | 5 | 接続・編集設定。現在スプシは非公開。編集キーを置くため今後も共有範囲を保つ |
| map_info | 16 | 9 | ピン本体。写真9件、音声付き0件。日時と文字列の保存規約を修正する |
| share_links | 10 | 0 | 有効化・失効を伴う共有リンク。必要 |
| routes | 14 | 0 | ピンから組み立てるルート。GPX用tracksとは別の役割 |
| route_pins | 5 | 0 | ルートへの所属と順序。別テーブルが妥当 |
| route_cache | 6 | 0 | 道路経路の再利用。容量・期限の運用を補う |
| tracks | 22 | 1 | GPX/GeoJSONのメタデータ。現在498点のGPX1件 |
| track_segments | 8 | 1 | 座標の分割保存。巨大JSONを避ける設計は適切 |
| input_presets | 14 | 0 | 入力設定の再利用。機能を使う際に必要 |
| import_receipts | 21 | 34 | 二重登録防止・再試行・途中失敗の復旧。単なる削除可能なログではない |

今回の現物チェックでは、主キーの重複、ルート所属の参照切れ、孤立したトラック座標、成功履歴の参照先ピン欠落、緯度経度範囲外は0件。GPXのメタデータ点数と座標行の点数、座標JSONの配列長も一致した。失敗履歴25件には保存済みfileIdがなかった。ただしDrive全ファイルとの突合までは行っておらず、孤立ファイルが絶対にないという判定ではない。

今後補うとよい設計は次の3点。

1. **列順の変更を検出する。** `map_info` は列番号固定で読む一方、`openMapInfoSheet_` は存在確認のみ。列挿入や並べ替えで誤った列を読み書きし得る。`tracks` と同様のヘッダー検証を設け、管理用シート・ヘッダーの手編集方針を明示する。実データでは列順の不整合はない。
2. **履歴の保持と検索方法を設計する。** `findImportReceipt_` はキー列の全走査、Drive重複判定は履歴全行を読む。取込件数が増えると繰り返しI/Oが増える。完了履歴を消すと二重登録防止やソース保護に影響するので、まず有効な参照・復旧待ち・失敗履歴を分け、保管と検索を設計する。現在34件の履歴が遅延の主因とは断定しない。
3. **スキーマの版と移行手順を明示する。** 設定や初期化の説明がコード更新に追随できるようにする。既存列を増やすこと自体より、型・互換性・整合性検証の統一を優先する。

## UI/UXの補足

- 再起動時の地図は全国表示から始まり、今回の9地点はほぼ重なって見えた。最後の表示位置を復元するか、全ピンへ合わせる分かりやすい操作があると閲覧開始が速くなる。これは機能改善案で、保存不具合ではない。
- 編集モードでは一覧の行クリックが選択、メニューは編集・削除中心で、写真閲覧への入口が地図側に寄っている。選択用チェックとタイトル／サムネイルの詳細表示を区別すると、写真を見たい利用者の手数を減らせる。
- 実写真1件の詳細表示、1920×1440の画像の読込完了、編集フォーム表示・キャンセルを確認した。現在音声付きピンが0件のため、実GASでの音声再生・置換・保存は未検証。
